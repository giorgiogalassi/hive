One issue from label to merge: how a GitHub event reaches an agent, what the engine does around the agent run, and how review and rework loop back. Chips show what each step reads (R) and writes (W) on GitHub or in the workdir; the matrix below maps every trigger to its outcome.

hive run --project <label> without a receiver

Lists issues with the label, orders them by dependencies (sub-issues, Depends-on: #N), and synthesises the same events into the same dispatch: Cody, wait for the PR, Reven, rework.

When a run fails

No result, an error, a timeout kill or iterations exhausted: the engine pushes the branch as it stands and comments on the issue. Skipped on main/master or when nothing was committed.

Reading the cells

In the webhook and hive run columns, R means that path receives the trigger; "synthesised" means the CLI builds the event itself instead of waiting for GitHub. W lists what Hive or the agent writes to GitHub.

Credentials

One GITHUB_TOKEN serves both agents. Exactly one Anthropic credential reaches the agent: ANTHROPIC_API_KEY if set, else CLAUDE_CODE_OAUTH_TOKEN. With a single token GitHub rejects Reven approving Cody's own PR, so expect human:review until agents get separate identities.

State lives in memory

The rework counters and in-flight set are per process and reset on restart. Labels on GitHub are the durable status; the workdir and its run.log are deleted after each run.
